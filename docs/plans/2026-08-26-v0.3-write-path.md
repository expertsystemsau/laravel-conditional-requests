# v0.3 Write Path Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Refuse a write that would clobber someone else's. `If-Match` is evaluated with strong comparison against the resource's current validator before the controller runs and a stale token is answered with `412 Precondition Failed`; `If-None-Match: *` guards a create against a concurrent duplicate; and the `required` flag turns a missing precondition into `428 Precondition Required` so the guard cannot be opted out of by simply omitting a header.

**Architecture:** `Conditional::handle()` gains a single branch on `Request::isMethodSafe()`. A safe method takes the v0.1/v0.2 read path, unchanged. An unsafe method takes a new `write()` method that never calls `$next()` until the precondition holds: it resolves the same strategy the read path would, asks it for the resource's *current* validator through `RequestValidatorStrategy::fromRequest()`, and hands request plus validator to a pure `PreconditionEvaluator`. The evaluator returns one of three outcomes and the middleware maps two of them onto `HttpException` subclasses that Laravel's existing exception handler renders as real `412`/`428` responses.

**Tech Stack:** PHP 8.3–8.5, Laravel 12–13, Pest 4/5, Orchestra Testbench, PHPStan level 7, Pint.

**Spec:** `docs/design/2026-08-25-conditional-requests-design.md` — §4 (strong vs weak), §5.1 (components), §5.2 (flags), §5.4 (write path), §7 (edge cases), §9 (phasing), §11 (werk365 parity and its defect table).

**Builds on:** `docs/plans/2026-08-26-v0.2-model-validators.md`, at its completed end state — `Flags`, `RequestValidatorStrategy`, `ModelStrategy`, `HasConditionalValidator`, the `tests/Fixtures` models, and the in-memory sqlite connection all exist, and the suite stands at 133 green tests.

- Root namespace is `ExpertSystems\ConditionalRequests\`.
- Type coverage gate is 100% (`composer test:types`); PHPStan runs at level 7 over `src` and `config` only. Config and translation reads return `mixed` — cast or filter. **The type-coverage plugin silently skips any file containing the string `trait `**, so `src/Concerns/HasConditionalValidator.php` is covered by PHPStan alone and a green gate is not proof for it. v0.3 adds no traits.
- Commit subjects match the existing history style — sentence case, imperative, no `feat:`/`fix:` prefixes.

The `lock` flag continues to parse and do nothing.

## Design decisions settled before planning

These were decided by the design and by the phase brief; they are restated here because several tasks depend on them and a worker should not re-litigate them mid-task.

**Strong comparison is not configurable away.** RFC 9110 §13.1.1 requires strong comparison for `If-Match`; §13.1.2 permits weak for `If-None-Match`. A weak validator can never satisfy `If-Match`, from either side of the comparison. This is defect #4 in the incumbent, whose `if_match_weak` defaults to `true`.

**A misconfiguration is a loud error, never a mystery 412.** A route flagged `required` whose strategy yields weak validators would refuse every write forever with no clue why. Task 5 makes that a `LogicException` naming `laravel-conditional-requests.weak`, raised the first time a guarded write reaches the middleware. §4's last bullet asks for this "at boot"; Task 5 documents why the first guarded request is the earliest point at which the check is *reliable*, and why a boot-time route scan would be a check with silent holes.

**Exceptions, not returned responses.** `Exceptions\PreconditionFailedException` and `Exceptions\PreconditionRequiredException` so applications customise rendering through the exception handler they already have.

**The evaluator is pure.** `Preconditions\PreconditionEvaluator` takes a `Request` and a `?Validator` and returns an enum. No container, no config, no response, no translations. Its whole rule set is exercised by unit tests.

### Task 1: The precondition evaluator

The comparison logic, on its own, before anything HTTP-shaped depends on it.

Symfony cannot help here. `Request::getETags()` (`vendor/symfony/http-foundation/Request.php:1627`) reads `If-None-Match` exclusively and `Response::isNotModified()` compares weakly — correct for the read path, wrong for `If-Match`. Nothing in HttpFoundation reads `If-Match` at all. This class is the half of RFC 9110 §13 the framework does not have.

Three parsing rules are worth naming up front, because each of them is a bug in the incumbent or a place a naive implementation goes wrong:

1. **The wildcard is bare and it is the whole field value.** The grammar is `If-Match = "*" / #entity-tag`. `werk365/etagconditionals` tests `in_array('"*"', $ifMatchArray)`, so a spec-compliant `If-Match: *` gets a spurious `412` there (defect #3). Here `*` is the wildcard and `"*"` is an entity tag whose opaque value happens to be an asterisk — and both are tested.
2. **A `W/`-prefixed entry is skipped under strong comparison, and a weak current validator fails it outright.** Either side being weak is enough to make `If-Match` unsatisfiable.
3. **A malformed entry never matches; it is never fatal.** `entity-tag = [ weak ] opaque-tag` and `opaque-tag = DQUOTE *etagc DQUOTE`, so a bare unquoted token is not an entity tag. §7 wants malformed headers ignored rather than fatal, and "never matches" is exactly what that means: `If-Match` then fails closed with `412`, `If-None-Match` fails open and the request proceeds.

```php
<?php

declare(strict_types=1);

namespace ExpertSystems\ConditionalRequests\Preconditions;

/**
 * What the evaluator decided about an unsafe request.
 *
 * Three states rather than a boolean, because "no precondition was sent" and
 * "the precondition that was sent does not hold" are different failures with
 * different answers — 428 tells a client to send one, 412 tells it the one it
 * sent is stale. Collapsing them is defect #2 in werk365/etagconditionals,
 * where an absent If-Match simply returns early and the guard becomes opt-out.
 */
enum PreconditionOutcome
{
    /**
     * The precondition holds, or there was none to hold. Run the controller.
     */
    case Passed;

    /**
     * A precondition was sent and does not hold — 412 Precondition Failed.
     */
    case Failed;

    /**
     * No precondition on a route that demands one — 428 Precondition Required.
     */
    case Required;
}
```

Create `src/Preconditions/PreconditionEvaluator.php`:

```php
<?php

declare(strict_types=1);

namespace ExpertSystems\ConditionalRequests\Preconditions;

use ExpertSystems\ConditionalRequests\Validators\Validator;
use Illuminate\Http\Request;

/**
 * Evaluates the RFC 9110 §13 preconditions that guard an unsafe request.
 *
 * Symfony owns the read path's comparison through Response::isNotModified(),
 * but nothing in HttpFoundation reads If-Match at all — Request::getETags()
 * (Request.php:1627) reads If-None-Match exclusively and compares it weakly,
 * which is the right rule for a read and the wrong one for a write. This class
 * is the half of §13 the framework does not have.
 *
 * The two comparisons are deliberately different:
 *
 *  - §13.1.1, If-Match, uses STRONG comparison. Both validators must be strong
 *    and their opaque tags octet-identical, so a weak validator on either side
 *    can never satisfy it.
 *  - §13.1.2, If-None-Match, uses WEAK comparison. The opaque tags must be
 *    octet-identical; either side may be weak.
 *
 * Nothing here touches the container, the configuration, or a response, so the
 * whole rule set is exercised by unit tests with a hand-built Request.
 */
final readonly class PreconditionEvaluator
{
    /**
     * Decide what should happen to an unsafe request.
     *
     * Precedence follows §13.2.2: If-Match is evaluated first, and If-None-Match
     * is consulted only in its absence. The `required` flag is what turns the
     * absence of any precondition from "proceed" into 428 — without it the
     * guard is opt-out and a client clobbers freely by omitting a header.
     */
    public function evaluate(Request $request, ?Validator $current, bool $required): PreconditionOutcome
    {
        $ifMatch = $this->header($request, 'If-Match');

        if ($ifMatch !== null) {
            return $this->outcome($this->isWildcard($ifMatch)
                ? $current instanceof Validator
                : $this->matchesStrongly($ifMatch, $current));
        }

        $ifNoneMatch = $this->header($request, 'If-None-Match');

        if ($ifNoneMatch !== null) {
            return $this->outcome($this->isWildcard($ifNoneMatch)
                ? ! $current instanceof Validator
                : ! $this->matchesWeakly($ifNoneMatch, $current));
        }

        return $required ? PreconditionOutcome::Required : PreconditionOutcome::Passed;
    }

    /**
     * Strong comparison of a field value against the current validator, per
     * RFC 9110 §13.1.1.
     */
    public function matchesStrongly(string $header, ?Validator $current): bool
    {
        // A weak validator asserts semantic equivalence, not byte equality, so
        // it cannot satisfy a precondition that requires strong comparison. It
        // is not configurable away: making it so is defect #4 in the incumbent.
        if (! $current instanceof Validator || $current->weak) {
            return false;
        }

        foreach ($this->tags($header) as $tag) {
            if (str_starts_with($tag, 'W/')) {
                continue;
            }

            if ($this->opaque($tag) === $current->etag) {
                return true;
            }
        }

        return false;
    }

    /**
     * Weak comparison of a field value against the current validator, per
     * RFC 9110 §13.1.2. Either side may be weak; the opaque tags must match.
     */
    public function matchesWeakly(string $header, ?Validator $current): bool
    {
        if (! $current instanceof Validator) {
            return false;
        }

        foreach ($this->tags($header) as $tag) {
            if ($this->opaque($tag) === $current->etag) {
                return true;
            }
        }

        return false;
    }

    /**
     * A header's value, or null when it is absent or blank.
     *
     * Corrected after the Task 1/2 review: If-None-Match alone reads its field
     * value this way, because zero members there means nothing matched and
     * §13.1.2 is satisfied either way. If-Match must NOT collapse blank to
     * absent — see sentHeader() in the shipped class — or a blank field value
     * fails open and clobbers.
     */
    private function header(Request $request, string $name): ?string
    {
        $value = $request->headers->get($name);

        if ($value === null || trim($value) === '') {
            return null;
        }

        return $value;
    }

    /**
     * Whether the entire field value is the bare wildcard.
     *
     * The grammar is `If-Match = "*" / #entity-tag`: the wildcard is unquoted
     * and it is the whole field value, not a member of the tag list.
     * werk365/etagconditionals looks for a quoted `"*"` inside the list, so a
     * spec-compliant `If-Match: *` gets a spurious 412 there — defect #3. Here
     * `"*"` is an entity tag whose opaque value happens to be an asterisk, and
     * it is compared as one.
     */
    private function isWildcard(string $header): bool
    {
        return trim($header) === '*';
    }

    /**
     * Split a field value into its entries, discarding optional whitespace and
     * empty members.
     *
     * @return list<string>
     */
    private function tags(string $header): array
    {
        $tags = [];

        foreach (explode(',', $header) as $tag) {
            $tag = trim($tag);

            if ($tag !== '') {
                $tags[] = $tag;
            }
        }

        return $tags;
    }

    /**
     * The opaque tag inside an entity tag, or null when the entry is malformed.
     *
     * `entity-tag = [ weak ] opaque-tag` and `opaque-tag = DQUOTE *etagc
     * DQUOTE`, so a bare unquoted token is not an entity tag and matches
     * nothing. §7 wants malformed headers ignored rather than fatal, and
     * "matches nothing" is what that means here: If-Match then fails closed
     * with 412, If-None-Match fails open and the request proceeds.
     */
    private function opaque(string $tag): ?string
    {
        if (str_starts_with($tag, 'W/')) {
            $tag = substr($tag, 2);
        }

        if (strlen($tag) < 2 || ! str_starts_with($tag, '"') || ! str_ends_with($tag, '"')) {
            return null;
        }

        return substr($tag, 1, -1);
    }

    private function outcome(bool $passed): PreconditionOutcome
    {
        return $passed ? PreconditionOutcome::Passed : PreconditionOutcome::Failed;
    }
}
```

### Task 2: The 412 and 428 exceptions, and the messages they carry

`lang/en/messages.php` has held a placeholder since v0.1 waiting for exactly this copy. Fill it, and give the two failures types an application can catch.

Both exceptions extend the Symfony exception for their own status code rather than `HttpException` directly. `PreconditionFailedHttpException` and `PreconditionRequiredHttpException` are themselves `HttpException` subclasses that hard-code 412 and 428, so this satisfies the "extends `HttpException`" requirement transitively, keeps us from repeating the status code, and means an application already catching Symfony's type keeps catching ours.

Each class carries the translation key for its own default message as a typed class constant, so the key and the exception stay together and the middleware never spells a translation key out inline.

### Task 3: The write path — `If-Match` and `required`

Wire the previous two tasks into `Conditional`. This is the task that makes the package do the thing it exists for.

`handle()` gains one branch, on `Request::isMethodSafe()` — Symfony's own list of GET, HEAD, OPTIONS, TRACE and the draft QUERY method. A safe method takes the v0.1/v0.2 read path with no change whatsoever. An unsafe one takes `write()`, which never reaches `$next()` until the precondition holds: a refusal issued after the controller has run is not a refusal.

Four things about the branch are deliberate and each has a test below:

- **`methods` does not gate the write path.** Its default is `['GET', 'HEAD']` and its documented meaning is read-path eligibility, so gating the write path on it would leave `conditional:required` doing nothing out of the box. Adding the unsafe methods to the default instead would start attaching validators to `POST` responses, which is a behaviour change to v0.1. The key keeps its meaning and its default; the write path applies to every unsafe method, per §5.4 and defect #1 — restricting to `PATCH` as the incumbent does misses MDN's own wiki-save-over-`POST` example. Task 7 sharpens the config comment to say so.
- **`enabled` and `exclude` still govern both paths.** They are the two switches an operator reaches for when something is wrong in production, and a guard that ignores the master switch is worse than no guard.
- **`exclude` is evaluated once on the write path, not twice.** The read path checks it a second time after `$next()` so that a route-*name* exclusion works under kernel-global placement, where nothing has been routed on the first check. The write path has no second chance by construction — its whole job is to decide before the controller — so under global placement a route-name exclusion cannot suppress it. Under global placement no model can be found either, which Task 6 covers.
- **A strategy that cannot answer from the request leaves the write untouched.** With no flags the strategy is the configured default, `body`, and a body hash cannot describe a response that does not exist yet. Rather than fail every precondition against a permanently-null validator, the request passes through exactly as it did before this phase. That keeps `tests/Feature/EligibilityTest.php`'s `POST` case green without editing it, and it keeps the promise that a route without `required` behaves as it does today. Pairing `required` with such a strategy is a configuration error, and Task 5 raises it.

```php
    /**
     * Guard an unsafe request against the resource's current validator.
     *
     * Everything here happens before $next(). The point of the write path is to
     * refuse a write that would clobber someone else's, and a refusal issued
     * after the controller has run is not a refusal — the update is already
     * lost. Nothing downstream ever sees a request whose precondition failed.
     *
     * @param  Closure(Request): Response  $next
     */
    private function write(Request $request, Closure $next, Flags $flags): Response
    {
        // The write path checks the exclusions once, not twice as the read path
        // does. It has no second chance by construction: the decision must
        // precede the controller, so a route-name exclusion cannot be honoured
        // under kernel-global placement, where nothing has been routed yet.
        if (! $this->enabled() || $this->excluded($request)) {
            return $next($request);
        }

        $strategy = $this->registry->strategy($this->strategyName($flags));

        if (! $strategy instanceof RequestValidatorStrategy) {
            // A body hash describes a response that does not exist yet, so
            // there is nothing to compare and nothing this path can guard. The
            // request passes through unchanged rather than failing every
            // precondition against a validator that is permanently null.
            return $next($request);
        }

        $current = $strategy->fromRequest($request);

        return match ($this->evaluator->evaluate($request, $current, $flags->required)) {
            PreconditionOutcome::Failed => throw new PreconditionFailedException(
                $this->message(PreconditionFailedException::MESSAGE_KEY),
            ),
            PreconditionOutcome::Required => throw new PreconditionRequiredException(
                $this->message(PreconditionRequiredException::MESSAGE_KEY),
            ),
            PreconditionOutcome::Passed => $next($request),
        };
    }
```

### Task 4: The wildcards — `If-Match: *` and the `If-None-Match: *` create guard

Both wildcards turn on one question: does the resource exist? The evaluator already answers it; this task proves the answer is right end to end and pins down what "exists" means.

**Existence is defined as: the write path's strategy returned a non-null `Validator` for this request.** Non-null means it exists; null means it does not. That definition has to be checked against what v0.2's trait actually returns, because `HasConditionalValidator::conditionalValidator()` returns `null` in three different situations that the write path cannot tell apart:

1. an unsaved record — no key, no version;
2. a saved record with a key but no usable version at all — no `version` column and no timestamps;
3. no record on the route at all.

**Is an unsaved-but-present model distinguishable from an absent one, and does it matter for `If-None-Match: *`?** No, and no. It is not distinguishable — both collapse to `null`. And it does not matter, because for `If-None-Match: *` the two want the same answer: a record that has never been saved does not exist as far as any client is concerned, so the create proceeds. An unsaved model can only reach a route parameter if the application bound one deliberately; ordinary `SubstituteBindings` never produces one.

Case (2) is the one that is genuinely lossy, and it is lossy against `If-Match: *` rather than `If-None-Match: *`: a saved record whose model keeps no version reads as absent, so `If-Match: *` refuses with `412` forever. That is fail-closed rather than fail-open, which is the right direction, but it is a trap and Task 7 documents it. The fix is a `version` column or timestamps on the model, which is the same rule v0.2 already documents for the read path.

**The create guard needs a binding that can produce "absent".** Under plain `SubstituteBindings`, a missing record is a `404` from the binder before the middleware ever runs, so the middleware only ever sees resources that exist. A create guard is therefore only meaningful on a route that *addresses* the resource being created — `PUT /articles/{article}` with a client-chosen key — and whose binder returns `null` rather than aborting. `Route::bind()` with a callback does exactly that: `RouteBinding::forCallback()` returns the callback unwrapped, so a `null` return substitutes `null` and nothing aborts. That is the fixture below, and it is the pattern Task 7 documents.

### Task 5: Configuration errors instead of permanent 412s

Two configurations make every guarded write fail forever with no clue why. Design §4's last bullet and §11.4 both want them to be errors rather than silent refusals.

**The weak-validator error.** RFC 9110 §13.1.1 requires strong comparison, so a weak validator can never satisfy `If-Match`. A route flagged `required` whose strategy yields weak validators — the `weak` config key set to `true` — refuses every write with `412` and there is nothing in the response to say why.

**The wrong-strategy error.** `required` implies `model` (v0.2, §5.2), but v0.2 deliberately lets an explicit strategy flag win, so `conditional:body,required` selects `body`. A body hash cannot produce a validator before the controller runs, so the guard silently does nothing. v0.2's own Out of Scope section names turning that from an honoured override into an error as v0.3's job.

**Where these are raised, and why not at boot.** §4 says "detected and thrown at boot". A boot-time scan of the route collection is not the right instrument here, for three reasons:

1. It cannot see every guarded route. `Route::gatherMiddleware()` returns route and group middleware but not controller-declared middleware, which `Router::gatherRouteMiddleware()` merges in only at dispatch. A check that silently skips a class of routes is worse than one that always fires, because it teaches you to trust it.
2. It cannot see the fact that matters. At boot the only observable is the `weak` config key. A custom strategy can emit weak validators with that key false, or strong ones with it true. The thing the guard actually breaks on is the weakness of the validator that comes back, and that is not knowable until a request has one.
3. It costs a full route-collection walk on every non-cached request, to check a condition that is false in every correctly-configured application.

Both errors are therefore raised in `write()`, on the first guarded unsafe request the route serves. That is unmissable in development and in CI — any test of a guarded route hits it immediately — and it is the earliest point at which the check is *reliable*. Both are `LogicException`, matching the registry's existing `InvalidArgumentException` for the other programming error in this package, and both name the exact thing to change.

Neither error fires without `required`. A route that never asked for the guard is never broken by it, which is the phase's hardest constraint.

### Task 6: Eligibility and graceful degradation on the write path

Everything the write path must do when it is *not* in the happy case: switched off, excluded, placed where it cannot see a model, or asked to guard a route it was never wired for. Each of these has a wrong answer that is worse than the feature not existing.

The `methods` config key is the interesting one. Its default is `['GET', 'HEAD']` and its documented meaning is read-path eligibility. Two tests pin down what it now means: an unsafe request is guarded even though its method is not in the list, and adding an unsafe method to the list does **not** make that method start receiving validators. The key keeps its meaning, its default, and its comment intent; Task 7 makes the comment say so out loud.

Kernel-global placement is the other. `ModelStrategy::fromRequest()` returns `null` when nothing has been routed, so a globally-placed guard sees every resource as absent. That has to degrade predictably rather than error: `If-Match` fails closed with `412`, an unguarded write proceeds, and nothing throws. The same is true of the more likely mistake — `conditional` listed before `SubstituteBindings` — and there the consequence is sharper than on the read path. v0.2's read path degrades gracefully to a slower `304`; the write path degrades to a `412` on every write. That asymmetry is the reason Task 7 documents the ordering as a requirement for guarded routes rather than a recommendation.

````markdown
### Guarding a create

`If-None-Match: *` is the mirror image: it succeeds only when the resource does **not** already exist. Two clients racing to create the same resource then produce one success and one `412`, instead of a silent duplicate or one overwriting the other.

```http
PUT /articles/42
If-None-Match: *
→ 200 OK                    # created

PUT /articles/42
If-None-Match: *
→ 412 Precondition Failed   # someone else created it first
```

For the guard to be able to answer, the route has to address the resource being created and its binding has to be able to report "absent" rather than aborting. Implicit binding raises a `404` for a missing record before the middleware ever runs, so register an explicit binder that returns `null`:

```php
Route::bind('article', fn (string $value): ?Article => Article::query()->find($value));
```

On a collection route such as `POST /articles` there is no bound resource to ask about, so the create guard has nothing to compare and the request proceeds.

### Requirements and caveats for guarded routes

> [!IMPORTANT]
> `conditional:required` must run **after** `SubstituteBindings`, and its model must produce a validator. Inside the `api` or `web` middleware group the ordering is already right. Get it wrong — kernel-global placement, or a hand-written list that puts `conditional` first — and the guard finds no record, treats every resource as absent, and refuses **every** `If-Match` with `412`. On the read path a wrong ordering only costs the compute saving; on the write path it stops writes.

> [!IMPORTANT]
> A model with no `version` column and no timestamps produces no validator, and a resource with no validator reads as absent. `If-Match: *` on such a route returns `412` every time. Add a `version` column or enable timestamps — the same rule the read path already needs.

> [!WARNING]
> Setting `weak => true` and flagging a route `required` is a configuration error and throws a `LogicException` on the first guarded request, naming the config key. A weak validator can never satisfy `If-Match`, so the pair would refuse every write with `412` and nothing in the response would say why. The same applies to naming a strategy that cannot produce a validator before the controller runs, such as `conditional:body,required`.

> [!NOTE]
> `If-Match` is evaluated first, per RFC 9110 §13.2.2; `If-None-Match` is consulted only in its absence. `If-Unmodified-Since` is not implemented yet, which means it does **not** satisfy `required` — a request carrying only that header still gets `428`.

> [!NOTE]
> `If-Match` closes the window between the client's read and its write, not the window between this check and the controller's own write. Two writes that both pass the guard microseconds apart can still race. `lock` mode, which re-evaluates the precondition inside a transaction holding a row lock, is on the roadmap.

Both refusals are `Symfony\Component\HttpKernel\Exception\HttpException` subclasses, so your application's existing exception handler renders and customises them:

```php
use ExpertSystems\ConditionalRequests\Exceptions\PreconditionFailedException;

$exceptions->render(function (PreconditionFailedException $e) {
    return response()->json(['error' => 'stale'], 412);
});
```

Their default bodies live in `lang/en/messages.php`; publish it with the `laravel-conditional-requests-lang` tag to reword them.
````

## Deliberately Out of Scope

Carried to later phases, per spec §9:

- `Last-Modified`, `If-Modified-Since`, and `If-Unmodified-Since` — v0.4. This is why **`If-Match` is the only update guard this phase**, and why `If-Unmodified-Since` alone does not satisfy `required`. v0.4 also adds `lastModified` to `Validator` as a trailing optional constructor argument and inserts the `If-Unmodified-Since` branch into `PreconditionEvaluator::evaluate()` after the `If-None-Match` branch, per §13.2.2.
- `lock` mode, in-transaction re-evaluation, and the whole of §5.5 — transaction ownership, nested transactions, savepoints, `afterCommit` job dispatch, long-transaction row-lock duration, and throwing when the strategy has no lockable row — v0.5. The `lock` flag continues to parse and do nothing. The TOCTOU window between this phase's check and the controller's write is real, documented in the README, and closed in v0.5.
- The `werk365/etagconditionals` migration guide — v1.0. This phase closes defects #1, #2, #3, #4, and #9 from §11.2; #5, #6, and #8 remain.

Considered and deliberately not built this phase:

- **Attaching a validator to a successful write's response.** A `PUT` that returns the updated resource could carry the new `ETag` and save the client a refetch. It is a genuinely useful feature, but it is a *read*-path concern wearing a write-path hat, it changes what an unsafe response looks like for every existing user of the middleware, and it needs the post-write validator, which means resolving the model a second time after the controller. Out of scope for a phase whose job is refusing writes.
- **A `required` config key** that turns the guard on globally. `required` is a per-route decision by design — §5.2 makes it a flag — and a global switch would turn every write in an application into a `428` the moment it was flipped. Nothing in this phase needs it, so v0.3 adds no config keys at all.
- **Naming the target route parameter**, revisited from v0.2's deferral. The write path produced no case for it: a guarded route addresses one resource, and that resource is the outermost route parameter. First-match on declaration order still holds.
- **Distinguishing "the strategy could not answer" from "the resource is absent"** through a new contract method. Both collapse to a `null` validator, which `If-Match` reads fail-closed and `If-None-Match: *` reads fail-open. The fail-open side is *acceptable*, not harmless: a create against a record that exists but yields no validator passes the only precondition meant to stop it, and the first writer is silently overwritten. It stands because closing it needs a separate existence question on the contract — a genuinely absent resource produces the same `null`, so a fail-closed create guard would refuse every legitimate create. That tri-state contract would be a public API addition serving one documented caveat, and `lock` mode in v0.5 has to revisit resource resolution anyway — better to design it once, with that phase's requirements in hand. `PreconditionEvaluator::evaluate()` carries the same note in its docblock.
- **A boot-time route scan** for the two configuration errors. Task 5 sets out the three reasons: it cannot see controller-declared middleware, it cannot see the weakness of a validator that has not been produced yet, and it costs a route-collection walk per request to check something false in every correct application.

## Controller addendum, added at execution time

**`If-Match: *` must NOT inherit v0.2's wildcard rule.** v0.2 deliberately refuses to
short-circuit on a bare `If-None-Match: *` (and on `W/*`), because on a read that token
is an existence probe: it produced an unauthenticated `304`/`404` oracle behind
authorization middleware that never ran. On the WRITE path the meaning is inverted —
`If-Match: *` is a legitimate precondition meaning "any current representation", and it
must be honoured, succeeding when the resource exists and failing `412` when it does not.
Same token, opposite handling, different header. Do not copy the read-path rule across.

Note also, for the `If-None-Match: *` create guard: strip the weakness prefix BEFORE
testing a candidate against `*`. Symfony strips first and v0.2's guard originally did
not, which let `W/*` behave as a concrete tag to us and as a wildcard to Symfony.
