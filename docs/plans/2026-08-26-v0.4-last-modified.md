# v0.4 `Last-Modified` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship the second half of RFC 9110's validators. Eligible responses advertise `Last-Modified` alongside their `ETag`; a client can revalidate a read with `If-Modified-Since` and guard a write with `If-Unmodified-Since`. The whole phase turns on one hazard — HTTP-date has one-second granularity and a record's modification time does not — and the rule that closes it is stated once, applied once, and tested at the microsecond.

**Architecture:** `Validator` gains a third field, `lastModified`, as a trailing optional constructor argument. `HasConditionalValidator` derives it from the record's `updated_at` and is the **only** place the one-second-granularity rule lives: a modification instant whose second has not finished yet is not published at all. `Conditional` sets the date on the response with Symfony's `setLastModified()` and lets `Response::isNotModified()` do the read-path comparison exactly as it already does for `If-None-Match` — the read path is a two-line change, not a reimplementation. The write path is ours: `PreconditionEvaluator` gains an `If-Unmodified-Since` branch at RFC 9110 §13.2.2's step 2, between `If-Match` and `If-None-Match`, and the middleware needs no change at all to pick it up.

**Tech Stack:** PHP 8.3–8.5, Laravel 12–13, Pest 4/5, Orchestra Testbench, PHPStan level 7, Pint.

**Spec:** `docs/design/2026-08-25-conditional-requests-design.md` — §4 (strong vs weak), §5.1 (components), §5.3 (read path), §5.4 (write path), §7 (edge cases), §9 (phasing), §11 (parity, defect #8).

**Builds on:** the v0.3 write path at its completed end state — `PreconditionEvaluator`, `PreconditionOutcome`, the `412`/`428` exceptions, `Conditional::write()`, the `label()`/`message()`/`enabled()` helpers, and a suite standing at 220 green tests.

## Design decisions settled before planning

These were settled by the design and the phase brief. They are restated here with their reasoning because most of the tasks below depend on them, and a worker should not re-litigate them mid-task.

### D1 — `Validator` gains `lastModified` as a trailing optional argument, and never carries a date alone

v0.1 left the field out deliberately and recorded that a later phase would add it this way, because a new optional trailing parameter breaks no existing caller. `Validator` stays `final readonly`.

**The property type is `?DateTimeImmutable`; the constructor parameter is `?DateTimeInterface`.** The parameter is widened for callers: Eloquent hands out `Illuminate\Support\Carbon`, which extends the **mutable** `DateTime`, and a value object that refused it would make every producer convert first. The property is narrowed for the object's own integrity: `readonly` protects the reference, not the referent, so a `final readonly` class holding a mutable `DateTime` has observably mutable state — a caller keeping the Carbon it passed in could `->addDay()` it and silently rewrite a validator that has already been compared. `DateTimeImmutable::createFromInterface()` copies, which closes that hole. An `int` of epoch seconds would also work and would compare natively, but it reads as a magic number everywhere it appears, and both `Response::setLastModified()` and `Response::getLastModified()` speak `DateTimeInterface` already.

**The stored value is floored to the whole second and normalised to UTC by the constructor.** That is not cosmetic: it is the invariant that makes every downstream comparison honest. `Last-Modified` is emitted at one-second granularity, so a validator whose in-memory value carries microseconds is a validator that compares differently from the header it produced. Flooring at construction means no consumer can forget to truncate, and `Validator::$lastModified` is exactly, byte for byte, what went on the wire.

**A validator always carries an entity tag; `Last-Modified` alone is not permitted.** `$etag` stays the first, required, non-empty-validated parameter. Three reasons, in order of weight:

1. Nothing in this package produces a date-only validator. `ModelStrategy` derives the tag from table + key + version, and `BodyHashStrategy` from the body; both have a tag whenever they have anything at all.
2. Since v0.3, *"the strategy returned a `Validator`"* **is** the write path's definition of "the resource exists" — it is what `If-Match: *` and `If-None-Match: *` are answered from. Making the tag optional would mean every one of those call sites has to re-ask what a tag-less validator means for existence, for a case no strategy can produce.
3. It keeps `header()` total, keeps `matchesStrongly()`/`matchesWeakly()` from having to handle a null tag, and keeps a `required` route safe: a date can never satisfy `If-Match` (§13.1.1 wants an entity tag), so a date-only validator on a guarded route would refuse every write.

An application that genuinely wants date-only revalidation can override `conditionalValidator()` and derive an entity tag from the timestamp — which is strictly better, because that tag *is* a strong validator and the date is not.

### D2 — one-second granularity, and the one rule that closes it

**This is the phase.** Everything else is wiring.

`Last-Modified` is an HTTP-date (RFC 9110 §5.6.7) and an HTTP-date has whole-second resolution. A record's modification instant does not: Eloquent's default `$dateFormat` happens to be `'Y-m-d H:i:s'`, which truncates on the way into the database, but any application that cares about ordering configures `datetime(6)` and a `'Y-m-d H:i:s.u'` format, and Postgres does it by default. So the value we are asked to advertise is `12:00:00.700` and the value we can advertise is `12:00:00`.

**Truncate, never round.** Rounding `12:00:00.700` up to `12:00:01` advertises a modification that has not happened yet: a change landing at `12:00:00.900` — after the real modification, before the advertised one — becomes invisible to every client holding `12:00:01`, forever. Rounding up can also push `Last-Modified` past the response's own `Date`, which RFC 9110 §8.8.2.2 forbids outright for a server with a clock. `Response::setLastModified()` formats with `'D, d M Y H:i:s'`, which truncates, and `Validator` floors to match. Both directions of the rule are pinned by tests, including one before the epoch, where a naive "round to nearest" and a naive integer cast disagree about which way is down.

Truncation alone is not enough, and this is the part most implementations get wrong:

> A record is modified at `12:00:00.700`. We serve it and advertise `Last-Modified: 12:00:00`. At `12:00:00.900` it is modified again. A client that echoes `If-Modified-Since: 12:00:00` is told `304 Not Modified` while holding a representation that is 200ms stale.

Note what is *not* the cause. The second write is invisible because both writes fall inside the same advertised second — which happens just as readily with a whole-second column, where both writes literally store `12:00:00`. Widening the column's precision does not fix it; it is the wire format's granularity, not the column's.

RFC 9110 §8.8.2.2 names the exact condition under which a `Last-Modified` date may be treated as a strong validator by an origin server:

> …that origin server reliably knows that the associated representation did not change twice during the second covered by the presented validator.

We cannot know that about a second that is still running — another write can still land in it. We *can* know it about a second that has finished, because the value we are holding is the last modification in it by definition. So:

**The rule: a modification instant is publishable as `Last-Modified` only once the second containing it has fully elapsed. Until then the resource advertises no `Last-Modified` at all.**

In code that is one comparison, in one place, at the point of derivation:

```php
$modified->getTimestamp() >= $this->freshTimestamp()->getTimestamp()   // → publish nothing
```

`getTimestamp()` floors, so the comparison is "the modification is in the current second, or in the future". It closes three separate bugs at once:

1. **Sub-second truncation.** A record modified at `12:00:00.700` publishes nothing until `12:00:01`, by which point `12:00:00` is a complete and final answer.
2. **Two modifications in one second.** They can only both hide behind one advertised date if the date was advertised while that second was still open. It never is.
3. **A future-dated `updated_at`** — replica clock skew, or an application writing a date ahead of the server's clock. The same comparison suppresses it. Suppression rather than clamping to `now`, because clamping publishes a modification time that is not the record's, and a clamped value is by construction in the current second and would be suppressed anyway.

The cost is precisely bounded and worth naming: for the remainder of the second in which a record changed, its responses carry an `ETag` and no `Last-Modified`. The `ETag` is unaffected by any of this — it is derived from the raw `updated_at` at whatever precision the column stores, so it distinguishes `12:00:00.700` from `12:00:00.900` and keeps protecting the client during exactly the window in which the date cannot. That is the right division of labour: the entity tag is the strong validator, and `Last-Modified` is the one that has to earn the claim.

**Comparison operators, and why they differ by path.**

*Read path — `>=`, and it is Symfony's, not ours.* `Response::isNotModified()` computes `strtotime($ifModifiedSince) >= strtotime($lastModified)` and answers `304` when true. Equality **must** count as "not modified", because equality is the normal case: a client echoes back the date we gave it. With the rule above, equality is also sound — the client's date names a second that had already finished when we published it, so it is the final word on that second and the client holds the representation it produced.

*Write path — `<=`, and it is ours.* §13.1.4 makes the `If-Unmodified-Since` condition true when the representation's last modification date is *earlier than or equal to* the supplied date. Here the truncation runs the other way and the naive implementation fails closed instead of open: comparing the **raw** `12:00:00.700` against a client's `If-Unmodified-Since: 12:00:00` yields `700ms > 0` and refuses the write with `412` — forever, for a client doing exactly what the protocol asks. The comparison must therefore use the floored value on our side, which `Validator` guarantees by construction, and accept equality. The same emission rule keeps that sound: the client can only be holding `12:00:00` because we published it after that second closed.

*No date at all — `412`, fail closed.* When the current validator carries no `lastModified` — the model keeps no timestamps, the column is absent from the loaded attributes, the value is unparseable, the record changed within the current second, or the deployment turned emission off — an `If-Unmodified-Since` cannot be evaluated. The choice is to ignore the header and proceed, or to refuse. We refuse. A client sends `If-Unmodified-Since` precisely to be told "no" when the server cannot vouch for the state; silently proceeding turns the guard the client asked for into a no-op, which is werk365 defect #2 wearing different clothes. It also matches what v0.3 already does for `If-Match` with no current validator. Both ways of getting there are documented in Task 8 alongside the existing "a model with no version reads as absent" trap.

*A residual window, stated rather than glossed.* A client that invents an `If-Unmodified-Since` we never published — from its own clock, or from the response's `Date` — can still name a second in which two modifications occurred, and the truncated comparison cannot see the second one. That window is inherent to a one-second validator, which is why RFC 9110 calls `Last-Modified` implicitly weak and why `If-Match` exists. This package ships `If-Match` and the README points at it. What we guarantee is narrower and checkable: **a client using validators this package published is never told "unmodified" about a representation that changed.**

### D3 — the read path is Symfony's; three things remain

`Response::isNotModified()` (`vendor/symfony/http-foundation/Response.php:1103`) already implements the whole read-path comparison: it gates on `isMethodCacheable()`, prefers `If-None-Match` when both conditional headers are present per §13.2.2 steps 3 and 4, falls back to `strtotime($modifiedSince) >= strtotime($lastModified)`, and calls `setNotModified()` on a hit. We do not duplicate any of it. What remains is exactly three things:

1. **`attach()` must call `setLastModified()`** — after `setEtag()`, before `isNotModified()`.
2. **The pre-controller stub must carry it too.** v0.2's short-circuit builds a bare `IlluminateResponse`, sets the ETag on it, and asks Symfony. Without a `Last-Modified` on that stub, Symfony's date branch has nothing to compare and an `If-Modified-Since`-only request never short-circuits — it would 304 only the slow way, after the controller. One line, and the D3 compute saving extends to the date validator.
3. **Neither call may change the response's cache policy** — see the Cache-Control note under D6, which is the only genuinely surprising thing `setLastModified()` does.

Two upstream behaviours are worth knowing and neither needs work:

- **Malformed `If-Modified-Since` is already non-fatal.** Symfony compares with `strtotime()`, which returns `false` on garbage, and `false >= <int>` is `false`, so a malformed value produces a `200`. Note the trap this avoids: `HeaderBag::getDate()` **throws** `RuntimeException` on an unparseable value, so nothing in this package may call `$response->getLastModified()` or `$request->headers->getDate(...)`. Task 4 uses `headers->has('Last-Modified')` for the same reason, and Task 6 parses with `strtotime()`.
- **`setNotModified()` strips `Last-Modified` from the `304`** (`Response.php:1051`), along with `Content-Type`, `Content-Length`, and the rest; it keeps the `ETag`. Nothing must compensate, and the reason is D1: because a validator always carries an entity tag, every `304` we emit carries one. RFC 9110 §15.4.5 requires `ETag` on a `304` and permits `Last-Modified` only as a cache-update aid *"if the response does not have an ETag field"* — which ours always does. Meanwhile RFC 9111 §4.3.4 has the client keep the stored `Last-Modified` from the original `200` when a `304` does not restate it, so the client's next conditional request is unaffected. Task 5 pins this as an assertion so it cannot silently change.

### D4 — the write path is ours, and it goes at §13.2.2 step 2

`If-Unmodified-Since` appears nowhere in HttpFoundation. `PreconditionEvaluator` gains it, consulted only when `If-Match` is absent.

**It is evaluated before `If-None-Match`, not after.** RFC 9110 §13.2.2 orders the steps: (1) `If-Match`; (2) `If-Match` absent and `If-Unmodified-Since` present; (3) `If-None-Match`; (4) `If-Modified-Since`, GET/HEAD only. The v0.3 plan's forward-looking note in *Deliberately Out of Scope* says the branch goes "after the `If-None-Match` branch"; that is wrong and this plan does not follow it. Nothing shipped depends on the mistake — no v0.3 test sends `If-Unmodified-Since` — so inserting the branch in the correct position changes no existing behaviour. Task 6 covers the ordering with a test that discriminates between the two positions.

**This closes a gap v0.3 shipped with.** A client sending only `If-Unmodified-Since` to a `required` route currently gets `428`, because v0.3 recognised no date preconditions. After v0.4 it is honoured, and the README note saying otherwise is corrected in Task 8.

**`If-Modified-Since` is ignored on unsafe methods** (§13.1.3 restricts it to GET and HEAD), which needs no code: the write path never looks at it. **`If-Unmodified-Since` is honoured on unsafe methods only.** A strict §13.2.2 reading applies step 2 to safe methods too, so a GET carrying `If-Unmodified-Since` could be answered `412`. This package deliberately does not do that: the design assigns the header to the write path (§5.4, §7, the README's header reference), Symfony's read path has no hook for it, and `412` is a startling answer to a GET in a Laravel application. It is a knowing deviation, recorded in *Deliberately Out of Scope*.

### D5 — where the timestamp comes from

`HasConditionalValidator` derives it from the model's `updated_at`, through a new protected extension point:

- **No timestamps** (`$timestamps = false`, or `Model::withoutTimestamps()`): `usesTimestamps()` is false, no column, no date. The entity tag is unaffected.
- **`UPDATED_AT` set to null**: `getUpdatedAtColumn()` returns `null`, guarded by the same `is_string()` check the existing `conditionalVersionColumns()` already uses.
- **A custom `UPDATED_AT` column**: used as-is, since the column name is read from the model rather than hard-coded.
- **Null or absent `updated_at`**: the attribute is checked with `array_key_exists()` against the loaded raw attributes first, so a partially-selected model (`select('id')`) yields no date rather than a lazy relation lookup, and a null value yields no date.
- **An unparseable stored value**: caught and treated as no date. A validator is an optimisation and must never be the reason a request fails — the same reasoning as `Conditional::stringList()`, which degrades a malformed config value to a no-op instead of a `TypeError` deep in the stack.

The date is read through `getAttribute()` rather than the raw attribute array, because the raw value is a string in the model's `$dateFormat` and Eloquent's own cast is the one thing guaranteed to parse it. That is a deliberate difference from `conditionalVersion()`, which reads raw precisely to avoid casts; the reasons diverge because a version token wants the stored bytes and a date wants a `DateTimeInterface`.

**`BodyHashStrategy` emits no `Last-Modified`.** It has no modification date and the only two things it could invent are lies: `now()`, or the response's `Date`. Either would advertise "this representation was modified just now" on every single response, which (a) is false, (b) changes on every request even when the body has not, defeating the validator's purpose, and (c) is by construction always inside the current second — the exact value D2 exists to refuse. A body hash is a fingerprint of content, not a record of when it changed, and it stays one. Task 4 pins it with a test.

### D6 — one new config key, `last_modified`, defaulting to `true`

**Against a key:** every key is surface, and a deployment that does not want dates could simply not implement the timestamp. **For a key:** three things, of which the first is decisive.

1. **Emitting `Last-Modified` silently changes the response's cache policy.** `ResponseHeaderBag::computeCacheControlValue()` returns `'no-cache, private'` for a response with no explicit `Cache-Control` — and `'private, must-revalidate'` once `Last-Modified` is present, with the comment *"allows for heuristic expiration (RFC 7234 Section 4.2.2) in the case of Last-Modified"*. The difference is not academic: `no-cache` forces revalidation on every use, while `private, must-revalidate` with no freshness lifetime lets a browser apply heuristic freshness — commonly 10% of the document's age — and reuse its copy **without making a conditional request at all**. A package whose entire purpose is revalidation would then have made a resource stop revalidating.
2. **`Last-Modified` discloses when a record changed.** An `ETag` is an opaque hash; a date is activity metadata. Some resources should not publish it.
3. **A `werk365/etagconditionals` migration** may want byte-identical response headers at cutover.

Reason 1 is handled in code rather than by the key, because the key is opt-out and the surprise should not exist even when the feature is on: design §10 makes `Cache-Control` management a non-goal, so **attaching a validator must not change the response's cache policy**. Task 4 captures `Cache-Control` immediately before `setLastModified()` and restores it if Symfony's recomputation changed it. That fires only when the application expressed no policy of its own; an explicit `Cache-Control` set by the application already suppresses the recomputation and is left alone.

Reasons 2 and 3 still justify the key, and it is cheap. **`last_modified` defaults to `true`**, because the package's headline claim over the incumbent is all four conditional headers (§11.2 defect #8) and a feature nobody switches on is not shipped. The `CHANGELOG` records that responses gain a header, with the one-line opt-out.

**The key governs the whole family, not just emission.** With it false, responses carry no `Last-Modified`, `If-Modified-Since` cannot produce a `304` (we advertised no date to echo), and `If-Unmodified-Since` is refused with `412` under the fail-closed rule rather than silently ignored. One switch, one meaning: *this deployment does not take part in the `Last-Modified` family.*

**It is read in exactly one place** — the service provider, when it builds `ModelStrategy` — which is where `weak` is already read. Everything else follows from the strategy not putting a date on the validator; the evaluator stays pure and needs no config. A custom strategy therefore decides for itself, exactly as it already does for weakness, and Task 8 says so.

    /**
     * Reduce a modification instant to the whole second, in UTC.
     *
     * The copy is not incidental. Eloquent hands out Illuminate\Support\Carbon,
     * which extends the mutable DateTime, and `readonly` protects the reference
     * rather than the object behind it — without the copy, a caller holding the
     * same instance could mutate a validator that has already been compared.
     */
    private static function second(?DateTimeInterface $lastModified): ?DateTimeImmutable
    {
        if (! $lastModified instanceof DateTimeInterface) {
            return null;
        }

        $utc = DateTimeImmutable::createFromInterface($lastModified)->setTimezone(new DateTimeZone('UTC'));

        // setTime() with three arguments zeroes the microseconds, and it floors
        // in both directions — including before the epoch, where a naive cast
        // of a negative fractional timestamp rounds the wrong way.
        return $utc->setTime((int) $utc->format('H'), (int) $utc->format('i'), (int) $utc->format('s'));
    }

     * The column holding the record's modification date, or null when it has none.
     *
     * Override to point at a different column, or to return null on a model
     * that should publish no Last-Modified. Returning null does not affect the
     * entity tag, which keeps validating the record either way.
     */
    protected function conditionalLastModifiedColumn(): ?string
    {
        if (! $this->usesTimestamps()) {
            return null;
        }

        $column = $this->getUpdatedAtColumn();

        return is_string($column) ? $column : null;
    }

    /**
     * The record's modification instant, or null when it has none this response
     * can safely publish.
     *
     * The comparison at the end is the whole Last-Modified problem in one line.
     * An HTTP-date has one-second resolution (RFC 9110 §5.6.7), so a record
     * modified at 12:00:00.700 can only be advertised as 12:00:00 — and if it
     * is modified again at 12:00:00.900, a client echoing 12:00:00 back would
     * be told 304 while holding a stale representation. The same is true of a
     * whole-second column, where both writes literally store 12:00:00: it is
     * the wire format's granularity, not the column's.
     *
     * RFC 9110 §8.8.2.2 permits a date validator to be treated as strong only
     * when the server "reliably knows that the associated representation did
     * not change twice during the second covered by the presented validator".
     * That cannot be known about a second that is still running, and is always
     * true of one that has finished. So a date is published only once its
     * second has fully elapsed, which also suppresses a future-dated value
     * from a skewed clock — the same comparison, the other side of it.
     *
     * The cost is bounded: for the remainder of the second in which a record
     * changed, its responses carry an entity tag and no date. The tag is
     * derived from the raw column at whatever precision it stores, so it keeps
     * validating during exactly the window in which the date cannot.
     *
     * The clock is the model's own — freshTimestamp() is what Eloquent used to
     * write the column in the first place, it honours Carbon::setTestNow(), and
     * an application that overrides it gets one clock rather than two.
     */
    private function conditionalLastModified(): ?DateTimeInterface
    {
        $column = $this->conditionalLastModifiedColumn();

        if ($column === null || ! array_key_exists($column, $this->getAttributes())) {
            return null;
        }

        try {
            $modified = $this->getAttribute($column);
        } catch (InvalidArgumentException) {
            // A stored value the model's date format cannot parse. A validator
            // is an optimisation and is never the reason a request fails —
            // the same degradation Conditional::stringList() applies to a
            // malformed config value.
            return null;
        }

        if (! $modified instanceof DateTimeInterface) {
            return null;
        }

        return $modified->getTimestamp() >= $this->freshTimestamp()->getTimestamp() ? null : $modified;
    }

### Task 4: Emitting `Last-Modified`, without changing what the response says about caching

Two call sites — the post-controller attach and the pre-controller stub — and one rule about what must **not** change along with the header.

The Cache-Control problem is the reason this task is not two lines. `ResponseHeaderBag::computeCacheControlValue()` (`vendor/symfony/http-foundation/ResponseHeaderBag.php:239`) returns `'no-cache, private'` for a response whose application set no policy of its own, and `'private, must-revalidate'` as soon as a `Last-Modified` is present — Symfony's own comment says it "allows for heuristic expiration". The practical difference is that `no-cache` makes a browser revalidate every time, and `private, must-revalidate` with no freshness lifetime lets it reuse its copy for a heuristic fraction of the document's age **without making a conditional request at all**. Attaching a validator would then have stopped the resource being validated. Design §10 makes `Cache-Control` management a non-goal, so the header is put back exactly as it was.

```php
    /**
     * Publish the validator's modification date without changing what the
     * response says about caching.
     *
     * Both halves are deliberate. A date the application set itself is left
     * alone, for the same reason an application's own ETag is (§7) — and it is
     * checked with has() rather than getLastModified(), because
     * HeaderBag::getDate() throws on a value it cannot parse.
     *
     * The Cache-Control dance is the surprising half. Symfony recomputes an
     * unset Cache-Control the moment a Last-Modified appears
     * (ResponseHeaderBag.php:239), turning the conservative "no-cache, private"
     * into "private, must-revalidate" to allow heuristic expiration — which
     * lets a browser reuse its copy for a fraction of the document's age
     * without revalidating at all. A package whose whole purpose is
     * revalidation must not be what stops a resource revalidating, and design
     * §10 makes cache policy a non-goal, so whatever the response said before
     * is what it says after. An application that set a policy explicitly is
     * untouched either way: its own value suppresses the recomputation.
     */
    private function attachLastModified(Response $response, Validator $validator): void
    {
        if (! $validator->lastModified instanceof DateTimeImmutable || $response->headers->has('Last-Modified')) {
            return;
        }

        $cacheControl = $response->headers->get('Cache-Control');

        $response->setLastModified($validator->lastModified);

        if ($cacheControl !== null && $response->headers->get('Cache-Control') !== $cacheControl) {
            $response->headers->set('Cache-Control', $cacheControl);
        }
    }
```

### Task 6: `If-Unmodified-Since` in the evaluator

The half of §13 the framework does not have, extended. `Request::getETags()` reads `If-None-Match` and nothing in HttpFoundation reads `If-Unmodified-Since` at all.

Three rules decide the shape of this, and each is a place a naive implementation goes wrong:

1. **It sits at §13.2.2 step 2** — after `If-Match`, **before** `If-None-Match`. The v0.3 plan's forward note put it after `If-None-Match`; that is wrong, and the test below discriminates between the two positions.
2. **The comparison uses the floored date on our side and accepts equality.** Comparing a raw `12:00:00.700` against a client's `If-Unmodified-Since: 12:00:00` — the exact value we published — refuses the write with `412` forever. `Validator` floors at construction, so the comparison here is already second against second, and `<=` is what §13.1.4 specifies.
3. **No date means `412`, a malformed date means ignore.** §13.1.4 requires a value that is not a valid HTTP-date to be ignored, so it falls through and does not satisfy `required`. A validator with no date is the opposite case: the condition cannot be shown to hold, and a client that asked to be protected gets refused rather than silently unguarded.

Parsing is `strtotime()`, the same function Symfony uses for `If-Modified-Since` on the read path, so both directions of the family accept the same field values. It returns `false` on anything it cannot read, which is how "ignore" is detected. **Nothing here may use `HeaderBag::getDate()`, which throws.**

**Files:**
- Modify: `src/Preconditions/PreconditionEvaluator.php`
- Test: `tests/Unit/PreconditionEvaluatorTest.php`

**Interfaces:**
- Consumes: `Validator` (Task 1).
- Produces: `PreconditionEvaluator::unmodifiedSince(string $header, ?Validator $current): ?bool` — `true` satisfied, `false` refused, `null` "no opinion, the value is not a valid HTTP-date", matching the package's existing use of null for that (`ValidatorStrategy::fromResponse()`). Plus a private `httpDate(string $value): ?int`. `evaluate()`'s signature is unchanged, so **no middleware change is needed for the write path to honour the header**.

    /**
     * Whether an If-Unmodified-Since field value is satisfied by the current
     * validator, per RFC 9110 §13.1.4. Null means the value is not a valid
     * HTTP-date and must be ignored — "no opinion", not "satisfied".
     *
     * Two rules do the work here. The comparison accepts equality, because the
     * normal case is a client echoing back the date this package published;
     * refusing equality would make the header useless for its own purpose. And
     * the date on our side is already floored to the whole second by Validator,
     * because comparing a raw 12:00:00.700 against the 12:00:00 we published
     * would refuse that client's write forever.
     *
     * A resource with no date at all fails closed. The condition cannot be
     * shown to hold, and a client that sent this header asked to be refused
     * when the server cannot vouch for the state — proceeding would silently
     * turn the guard it asked for into a no-op.
     */
    public function unmodifiedSince(string $header, ?Validator $current): ?bool
    {
        $since = $this->httpDate($header);

        if ($since === null) {
            return null;
        }

        $modified = $current?->lastModified;

        if (! $modified instanceof DateTimeImmutable) {
            return false;
        }

        return $modified->getTimestamp() <= $since;
    }

    /**
     * An HTTP-date as a Unix timestamp, or null when it is not one.
     *
     * strtotime() is what Symfony's Response::isNotModified() uses for
     * If-Modified-Since, so both halves of the family accept exactly the same
     * field values — including all three formats §5.6.7 requires a recipient to
     * read. HeaderBag::getDate() would be the tidier call and is unusable: it
     * throws RuntimeException on a value it cannot parse, and §7 wants a
     * malformed validator header ignored rather than fatal.
     *
     * The blank check is load-bearing rather than defensive. strtotime('   ')
     * returns the *current time* instead of false, so a whitespace-only field
     * value reaching the parser would be read as "unmodified since now" and
     * satisfy every precondition it was asked about. evaluate() already treats
     * a blank header as absent; this makes the parser safe on its own terms.
     */
    private function httpDate(string $value): ?int
    {
        $value = trim($value);

        if ($value === '') {
            return null;
        }

        $timestamp = strtotime($value);

        return $timestamp === false ? null : $timestamp;
    }

### Last-Modified and If-Modified-Since

A model-derived validator publishes the record's modification date alongside its tag, so a client can revalidate with either.

```http
GET /articles/42
→ 200 OK
  ETag: "9b1c0e0f6b0a4f9d"
  Last-Modified: Wed, 26 Aug 2026 12:00:00 GMT

GET /articles/42
If-Modified-Since: Wed, 26 Aug 2026 12:00:00 GMT
→ 304 Not Modified          # the controller never ran
```

The date comes from `updated_at`. A model with no timestamps, a null `UPDATED_AT` column, or an unloaded `updated_at` publishes no date and keeps its tag; override `conditionalLastModifiedColumn()` to point at a different column, or to return `null` to suppress the date for a model entirely. > [!IMPORTANT]
> **A record that has just changed publishes no `Last-Modified` until the second it changed in has elapsed.** This is deliberate, and it is the one thing most `Last-Modified` implementations get wrong.
>
> An HTTP-date has one-second resolution. A record modified at `12:00:00.700` can only be advertised as `12:00:00` — and if it changes again at `12:00:00.900`, a client echoing `If-Modified-Since: 12:00:00` back would be told `304 Not Modified` while holding a stale representation. The same is true of a plain second-precision column, where both writes store `12:00:00`; widening the column does not help, because the limit is in the header format.
>
> RFC 9110 §8.8.2.2 allows a date to be treated as a strong validator only when the server knows the representation did not change twice inside the second it names. That is unknowable while the second is still running and always true once it has finished, so the date is published a moment later. In the meantime the `ETag` — which is derived from the raw column at full precision — keeps validating the resource, which is why the two headers ship together.

> [!NOTE]
> A `304` carries the `ETag` and no `Last-Modified`: RFC 9110 §15.4.5 requires the tag and wants the date only when there is no tag, and your client keeps the date it stored from the original `200` (RFC 9111 §4.3.4).

> [!NOTE]
> Set `last_modified => false` in the config to keep the whole family out of the conversation. Responses then carry no date, `If-Modified-Since` can never produce a `304`, and `If-Unmodified-Since` is refused rather than ignored. Attaching a date never changes what a response says about caching — the middleware restores the `Cache-Control` the response already had, so a validator can never be the reason a resource stops being revalidated.

## Deliberately Out of Scope

Carried to later phases, per spec §9:

- `lock` mode, in-transaction re-evaluation, and the whole of design §5.5 — v0.5. The `lock` flag continues to parse and do nothing. The TOCTOU window between the precondition check and the controller's write is real, documented in the README, and closed there.
- The `werk365/etagconditionals` migration guide — v1.0. This phase closes defect #8; #5 and #6 remain.

Considered and deliberately not built this phase:

- **`If-Unmodified-Since` on safe methods.** A strict reading of §13.2.2 applies step 2 to a GET, so a conditional read could be answered `412`. The design assigns the header to the write path throughout (§5.4, §7, the README's header reference), Symfony's read-path comparison has no hook for it, and `412` is a startling answer to a GET. Recorded as a knowing deviation rather than an oversight.
- **A tri-state "the resource has no date" versus "the date is unusable right now".** Both collapse to a null `lastModified` and both fail closed, so the distinction would only ever change an error message. It is the same collapse v0.3 accepted for resource existence, and for the same reason: a new contract method to serve one documented caveat is a public API addition that `lock` mode will want to revisit anyway.
- **A defensive clock check at emission.** The middleware could reject a validator whose date is in the future using the response's own `Date` header, catching a custom `ProvidesConditionalValidator` that ignores the rule. It would be a second clock read per response to defend against a case only a custom implementation can create, against the package's established position that strategies are trusted past a minimal well-formedness guard (`Validator::validate()`'s docblock). The requirement is stated in the trait's documentation instead.
- **Forcing `Cache-Control: no-cache` on dated responses.** Task 4 restores whatever the response already said; it does not impose a policy. Design §10 makes cache-control management a non-goal, and an application that deliberately set `private, must-revalidate` should keep it.
- **Deriving a `Last-Modified` for the body-hash strategy** from `now()` or the response `Date`. Both are false, both change on every request, and both name the current second — the exact value D2 exists to refuse. See D5.
- **A `Last-Modified`-only validator**, with the entity tag made optional. No strategy in the package can produce one, `Validator`-is-non-null is the write path's existence test since v0.3, and a date can never satisfy `If-Match`. See D1.
- **Widening `If-Modified-Since` handling beyond Symfony's.** Its `strtotime()` comparison accepts more than §5.6.7's three formats and does not reject a client date in the future. Reimplementing it to be stricter would mean owning the read-path comparison the package has delegated since v0.1, for no behaviour a client would notice.
