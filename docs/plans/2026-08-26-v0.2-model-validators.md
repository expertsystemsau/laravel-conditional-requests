# v0.2 Model-Derived Validators Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Derive the validator from the route-bound model's own version instead of a hash of the rendered body, and use it to answer a matching `If-None-Match` with `304` **before the controller runs**. v0.1 saved bandwidth; v0.2 saves the compute behind it.

**Architecture:** A second strategy contract, `RequestValidatorStrategy`, extends the existing one with `fromRequest()`. `ModelStrategy` implements it by scanning the current route's parameters for a bound model implementing `ProvidesConditionalValidator`, whose default trait builds a strong tag from the record's table, key, and version. The middleware resolves its strategy before `$next()`, and when the strategy can answer from the request alone it builds a stub response, hands it to Symfony's `isNotModified()`, and returns the resulting `304` without ever calling the controller. When the tags do not match — or when there is no model to ask — the request falls through to exactly the v0.1 path, reusing the validator it already computed.

**Tech Stack:** PHP 8.3–8.5, Laravel 12–13, Pest 4/5, Orchestra Testbench, PHPStan level 7, Pint.

**Spec:** `docs/design/2026-08-25-conditional-requests-design.md` — §4 (strong vs weak), §5.1–5.3 (components, flags, read path), §7 (edge cases), §9 (phasing).

### Task 2: The model contract and its default trait

The model side of the feature: a contract a record implements to speak for its own version, and a trait that implements it for an ordinary Eloquent model.

Three decisions are baked in here and are not negotiable downstream:

1. **The tag is strong.** Design §4: RFC 9110 §13.1.1 requires strong comparison for `If-Match`, so a weak model tag would make every `conditional:required` write fail with `412` in v0.3.
2. **The tag folds in identity as well as version.** Table, key, *and* version — two records with the same id and the same `updated_at` in different tables must not collide.
3. **No version means no validator.** An unsaved record, or one whose model keeps no timestamps and has no version column, returns `null`. Inventing a tag would hand the client something that can never match again.

The method takes the `Request` because §4 requires a hook for folding representation-affecting input — content negotiation, sparse fieldsets, includes — into a strong tag. The default implementation ignores it; overriding is how an application uses it.

```php
declare(strict_types=1);

namespace ExpertSystems\ConditionalRequests\Contracts;

use ExpertSystems\ConditionalRequests\Validators\Validator;
use Illuminate\Http\Request;

interface ProvidesConditionalValidator
{
    /**
     * The validator for this record's current version, or null when it has none.
     *
     * The request is passed so an implementation can fold representation-affecting
     * input — content negotiation, sparse fieldsets, includes — into the tag. A
     * strong validator asserts one specific representation, so a record served in
     * more than one shape has to vary its tag with the shape.
     */
    public function conditionalValidator(Request $request): ?Validator;
}
```

Create `src/Concerns/HasConditionalValidator.php`:

```php
<?php

declare(strict_types=1);

namespace ExpertSystems\ConditionalRequests\Concerns;

use ExpertSystems\ConditionalRequests\Validators\Validator;
use Illuminate\Http\Request;

/**
 * The default ProvidesConditionalValidator implementation for an Eloquent model.
 *
 * The tag fingerprints identity and version together: the table the record
 * lives in, its key, and either an explicit version column or the raw
 * updated_at value at whatever precision the column stores. Identity is in
 * there so that two records with the same key and the same timestamp, in
 * different tables, cannot be mistaken for one another.
 *
 * Model-derived validators are strong (design §4). RFC 9110 §13.1.1 requires
 * strong comparison for If-Match, so a weak tag here would reject every
 * guarded write on the v0.3 write path.
 *
 * @phpstan-require-extends \Illuminate\Database\Eloquent\Model
 */
trait HasConditionalValidator
{
    public function conditionalValidator(Request $request): ?Validator
    {
        $key = $this->getKey();
        $version = $this->conditionalVersion();

        // A record with no version has nothing for a client to agree on, and
        // inventing one hands out a tag that can never match again.
        if ($version === null || (! is_string($key) && ! is_int($key))) {
            return null;
        }

        return new Validator(hash('xxh128', implode("\0", [
            $this->getTable(),
            (string) $key,
            $version,
        ])));
    }

    /**
     * The columns consulted for a version token, in order of preference.
     *
     * Override to point at a different column, or to return an empty list on a
     * model that should never produce a validator.
     *
     * @return list<string>
     */
    protected function conditionalVersionColumns(): array
    {
        $columns = ['version'];

        if ($this->usesTimestamps() && is_string($column = $this->getUpdatedAtColumn())) {
            $columns[] = $column;
        }

        return $columns;
    }

    /**
     * The first usable version token on the record.
     *
     * Raw attributes are read rather than cast ones: the raw value is exactly
     * what the column holds, at exactly the precision it holds it, and it never
     * shifts because an application added a cast or an accessor for display.
     */
    private function conditionalVersion(): ?string
    {
        $attributes = $this->getAttributes();

        foreach ($this->conditionalVersionColumns() as $column) {
            $value = $attributes[$column] ?? null;

            if (is_int($value)) {
                return (string) $value;
            }

            if (is_string($value) && $value !== '') {
                return $value;
            }
        }

        return null;
    }
}
```

### Task 3: `RequestValidatorStrategy` and the model strategy

`ValidatorStrategy::fromResponse()` is untouched: every custom strategy written against v0.1 keeps working. What arrives is a sub-interface, `RequestValidatorStrategy`, adding `fromRequest()`. `instanceof` against it is how the middleware asks "can this strategy answer before the controller runs?", which is a question a body hash can never answer yes to.

`ModelStrategy` implements both halves. `fromRequest()` is the short-circuit source. `fromResponse()` resolves the same model the same way and returns the same validator, which is what keeps the response correct on every path where the short-circuit did not fire — a stale client tag, or kernel-global placement where nothing had been routed yet.

**On naming a specific route parameter:** not in v0.2, deliberately. The first route parameter implementing the contract wins, and route parameters keep their declaration order, so on `/articles/{article}/comments/{comment}` the article is the target and stays the target regardless of runtime state. A config key or a `conditional:model:comment` flag would add grammar to the flag list for a case — two conditional models on one route, where the wanted one is not the outermost — that has a working answer already: override `conditionalValidator()` on the model, or register a custom strategy. Revisit in v0.3 only if the write path produces a real case.

Note the deliberate rule: the first parameter *implementing the contract* is the target, not the first that *yields a validator*. If it declines, the strategy declines. Falling through to the next parameter would let the target move as records are saved.

```php
 * the state SubstituteBindings leaves behind, built by hand so these stay unit

 *
 * @param  array<string, mixed>  $parameters

function routedRequest(string $uri, string $pattern, array $parameters = [], bool $bind = true): Request
{
    $request = Request::create($uri);

    $route = new Route(['GET'], $pattern, fn (): null => null);
```

Create `src/Validators/ModelStrategy.php`:

```php
<?php

declare(strict_types=1);

namespace ExpertSystems\ConditionalRequests\Validators;

use ExpertSystems\ConditionalRequests\Contracts\ProvidesConditionalValidator;
use ExpertSystems\ConditionalRequests\Contracts\RequestValidatorStrategy;
use Illuminate\Http\Request;
use Illuminate\Routing\Route;
use Symfony\Component\HttpFoundation\Response;

/**
 * Derives a validator from a route-bound record's own version.
 *
 * The validator is known before the controller runs, so a matching
 * If-None-Match costs no controller execution, no queries, and no
 * serialization — this strategy saves compute, not just bandwidth.
 */
final readonly class ModelStrategy implements RequestValidatorStrategy
{
    public function __construct(private bool $weak = false) {}

    public function fromRequest(Request $request): ?Validator
    {
        $model = $this->target($request);

        if (! $model instanceof ProvidesConditionalValidator) {
            return null;
        }

        return $this->weaken($model->conditionalValidator($request));
    }

    /**
     * Resolve the same record from the same route once the controller has run.
     *
     * Needed whenever the short-circuit did not fire — the client's tag was
     * stale, or nothing had been routed when the middleware first looked — so
     * the response still leaves carrying the current validator.
     */
    public function fromResponse(Request $request, Response $response): ?Validator
    {
        return $this->fromRequest($request);
    }

    /**
     * The first route parameter that can speak for its own version.
     *
     * First rather than best: route parameters keep their declaration order, so
     * the outermost resource wins and the target never moves with runtime
     * state. If that parameter declines, so does this strategy.
     */
    private function target(Request $request): ?ProvidesConditionalValidator
    {
        $route = $request->route();

        // Null under kernel-global placement, where nothing has been routed
        // yet; unbound routes make Route::parameters() throw, so ask first.
        if (! $route instanceof Route || ! $route->hasParameters()) {
            return null;
        }

        foreach ($route->parameters() as $parameter) {
            if ($parameter instanceof ProvidesConditionalValidator) {
                return $parameter;
            }
        }

        return null;
    }

    /**
     * Model validators are strong by default (design §4). The `weak` config key
     * opts a deployment out of the guarantee on read-only routes; it can only
     * ever weaken a tag, never strengthen one the model marked weak itself.
     */
    private function weaken(?Validator $validator): ?Validator
    {
        if (! $validator instanceof Validator || ! $this->weak || $validator->weak) {
            return $validator;
        }

        return new Validator($validator->etag, weak: true);
    }
}
```

```php
<?php

declare(strict_types=1);

namespace ExpertSystems\ConditionalRequests\Http\Middleware;

/**
 * The parsed middleware parameter list.
 *
 * Design §5.2 makes flags order-independent and reserves words that name
 * behaviour rather than a strategy. `required` (v0.3) and `lock` (v0.5) are
 * reserved here, ahead of the releases that implement them, so that
 * `conditional:required` parses today instead of asking the registry for a
 * strategy of that name and throwing. Adding a reserved word later means
 * extending the chain in parse() and adding a flag to this object.
 */
final readonly class Flags
{
    private function __construct(
        public ?string $strategy,
        public bool $required,
        public bool $lock,
    ) {}

    /**
     * @param  list<string>  $flags
     */
    public static function parse(array $flags): self
    {
        $strategy = null;
        $required = false;
        $lock = false;

        foreach ($flags as $flag) {
            $flag = trim($flag);

            if ($flag === '') {
                continue;
            }

            if ($flag === 'required') {
                $required = true;
            } elseif ($flag === 'lock') {
                $lock = true;
            } elseif ($strategy === null) {
                $strategy = $flag;
            }
        }

        return new self($strategy, $required, $lock);
    }

    /**
     * The strategy to use: an explicit flag first, then the reserved-word
     * implication, then the configured default.
     *
     * §5.2 has `required` and `lock` imply `model`, because the write path must
     * know the current validator before the controller runs and a body hash
     * cannot supply one. An explicitly named strategy still wins — pairing
     * `required` with a strategy that cannot serve it becomes a boot-time error
     * in v0.3 rather than a silent override here.
     */
    public function strategyOr(string $default): string
    {
        if ($this->strategy !== null) {
            return $this->strategy;
        }

        if ($this->required || $this->lock) {
            return 'model';
        }

        return $default;
    }
}
```

### Task 5: The pre-controller short-circuit

The headline. With a model-derived validator the current version is known before the controller runs, so a matching `If-None-Match` can be answered immediately — the route action never executes.

Placement is exact: **after** `requestEligible()`, so `enabled`, `methods`, and `exclude` all still govern it, and **before** the `HEAD` method mutation and `$next()`, so nothing has been touched when it returns.

Three things about the returned `304` matter:

- `Response::setNotModified()` (`vendor/symfony/http-foundation/Response.php:1051`) sets the status, nulls the content, and removes `Allow`, `Content-Encoding`, `Content-Language`, `Content-Length`, `Content-MD5`, `Content-Type`, and `Last-Modified`. It keeps the `ETag`, which is what lets the client refresh its cache entry.
- `Response::isNotModified()` gates on `Request::isMethodCacheable()`, so `GET` and `HEAD` both qualify and an ineligible method could never short-circuit even if it reached here.
- `Router::toResponse()` (`vendor/laravel/framework/src/Illuminate/Routing/Router.php:942`) calls `setNotModified()` again on any `304` and then `prepare()`. Both paths — short-circuit and post-controller — converge on the same normalisation, which is exactly why the two are indistinguishable and why a test can assert it.

Resolving the strategy moves ahead of `$next()`. One consequence worth naming: a flag naming an unregistered strategy now throws *before* the controller runs rather than after, and it throws on requests whose response would have been ineligible anyway. That is strictly better feedback for what is always a programming error, and no existing test depends on the old timing.

### Task 6: Reuse the request-derived validator after the controller runs

The short-circuit only fires when the client's tag matches. Every other request through a model-derived route still has to leave with the current `ETag` on it, and right now that costs a second resolution of the same model to produce the same tag — `fromRequest()` before the controller, `fromResponse()` after it.

Two further things follow from a strategy that never looks at the body, and both are currently wrong:

- **The body-shaped skip rules do not apply to it.** Streamed and binary responses are skipped because hashing them means buffering them; the size ceiling exists so a large payload is not fingerprinted just to discover it changed. A validator taken from a record's version costs nothing to produce whatever the body is. Today a model-backed route returning a stream or a payload over the ceiling short-circuits happily *if* the client has a tag, but is never given one to hold — the feature quietly does not work there. Status and pre-existing-`ETag` checks still apply to every strategy: an error response never carries a validator, and an application's own tag is never overwritten.
- **The `HEAD` method mutation does not apply to it either.** Design §7 says so outright: model-derived validators read the record's version instead of the rendered body, so they do not need the mutation. Skipping it means a controller on such a route sees the `HEAD` the client actually sent. The single exit through `withoutBody()` stays exactly as it is — it is idempotent with what `Response::prepare()` already did.

```php
     * a validator derived from the request, which costs nothing whatever the
```

````markdown
### Model-derived validators

The `model` strategy takes the validator from the route-bound record rather than from the rendered body. Because the record's version is known **before** the controller runs, a request whose `If-None-Match` already matches is answered with `304` without executing the route action — no queries, no serialization.

Add the contract and the trait to the model:

```php

use ExpertSystems\ConditionalRequests\Concerns\HasConditionalValidator;
use ExpertSystems\ConditionalRequests\Contracts\ProvidesConditionalValidator;
use Illuminate\Database\Eloquent\Model;

class Article extends Model implements ProvidesConditionalValidator
{
    use HasConditionalValidator;
}
```

Then name the strategy on the route:

```php
Route::get('/articles/{article}', ShowArticle::class)
    ->middleware('conditional:model');
```

```http
GET /articles/42
→ 200 OK
  ETag: "9b1c0e0f6b0a4f9d"

GET /articles/42
If-None-Match: "9b1c0e0f6b0a4f9d"
→ 304 Not Modified          # the controller never ran
```

The default tag fingerprints the record's table, its key, and its version — an explicit `version` column when the model has one, otherwise the raw `updated_at` value. The table is in there so two records with the same id in different tables can never share a tag. A record with no version at all — one that has never been saved — produces no validator, and the response is left untouched.

Model-derived validators are **strong**. RFC 9110 §13.1.1 requires strong comparison for `If-Match`, so a weak tag could never satisfy the write-path guard.

> [!IMPORTANT]
> `conditional` must run **after** route model binding. Inside the `api` or `web` middleware group that is already true, since `SubstituteBindings` belongs to both. On a route that has not had its bindings substituted yet — kernel-global placement, or a hand-written middleware list that puts `conditional` first — the strategy finds no record before the controller runs and the request quietly takes the ordinary path: the `ETag` is still attached on the way out, but the controller runs and nothing is saved.

> [!NOTE]
> `updated_at` is stored to the second by default, so two writes inside the same second produce the same tag. Add a `version` column, or widen the column's precision, on resources that change that fast.

When a route binds more than one conditional record, the **first** route parameter implementing the contract wins — parameters keep their declaration order, so on `/articles/{article}/comments/{comment}` the article is the target.

#### Varying the tag by representation

A strong validator asserts one specific representation. If the same record is served in more than one shape — content negotiation, sparse fieldsets, `?include=` — fold that input into the tag. That is what the `$request` argument is for:

```php
use ExpertSystems\ConditionalRequests\Concerns\HasConditionalValidator;
use ExpertSystems\ConditionalRequests\Contracts\ProvidesConditionalValidator;
use ExpertSystems\ConditionalRequests\Validators\Validator;
use Illuminate\Database\Eloquent\Model;
use Illuminate\Http\Request;

class Article extends Model implements ProvidesConditionalValidator
{
    use HasConditionalValidator {
        conditionalValidator as baseConditionalValidator;
    }

    public function conditionalValidator(Request $request): ?Validator
    {
        $validator = $this->baseConditionalValidator($request);

        if (! $validator instanceof Validator) {
            return null;
        }

        return new Validator(hash('xxh128', $validator->etag."\0".(string) $request->query('fields')));
    }
}
```
````

- [ ] A repeated `GET` against a model-derived route returns `304` **and a controller-invocation counter proves the route action did not run**.
- [ ] A `HEAD` request short-circuits to `304` with an empty body.
- [ ] A short-circuited `304` is header-for-header identical to one produced after the controller ran, `Date` excluded.
- [ ] `conditional:required`, `conditional:lock`, and both orderings of the two parse, select the `model` strategy, and throw nothing.
- [ ] An explicit strategy flag still beats the reserved-word implication.
- [ ] Under kernel-global placement the short-circuit degrades to the v0.1 path: no error, the `ETag` still attached, the controller run.
- [ ] `enabled`, `methods`, and `exclude` all still suppress the short-circuit.
- [ ] `body` remains the default and every v0.1 behaviour is unchanged, with the single deliberate edit to the registered-strategy list pinned in `tests/Feature/StrategyRegistryTest.php`.
- [ ] `illuminate/database` is declared in `composer.json` and the lock is current.
- [ ] README documents the model strategy, the `SubstituteBindings` ordering requirement, the `updated_at` precision caveat, and the representation hook.

## Deliberately Out of Scope

Carried to later phases, per spec §9:

- `If-Match`, `412`, `428`, and the `If-None-Match: *` create guard — v0.3, which also adds the boot-time error for `required` on a strategy that yields weak validators, and turns `conditional:body,required` from an honoured override into that error.
- `Last-Modified`, `If-Modified-Since`, `If-Unmodified-Since` — v0.4, which adds `lastModified` to `Validator` as a trailing optional constructor argument.
- `lock` mode and in-transaction re-evaluation — v0.5. The flag parses now and does nothing.
- Populating `lang/en/messages.php`, whose empty return is untouched until v0.3 needs real `412` / `428` copy.

Considered and deliberately not built this phase:

- **Naming the target route parameter** through a config key or a flag such as `conditional:model:comment`. First-match on declaration order is deterministic and covers the ordinary case; the awkward case already has two answers — override `conditionalValidator()`, or register a strategy. Revisit only if v0.3 produces a real need.
- **Registering `Conditional` in the framework's middleware priority list** so it always sorts after `SubstituteBindings`. It would guarantee the ordering, but it silently reorders application middleware, changes behaviour for existing v0.1 users of the `body` strategy, and means resolving the HTTP kernel from a package provider. The failure mode without it is graceful and tested — the tag still lands, only the compute saving is lost — so documentation is the right size of fix.
- **Making the model tag's hash algorithm configurable.** The `hash` config key exists to trade throughput against collision resistance when fingerprinting a *payload*; the model tag fingerprints a short, entirely server-controlled identity string where neither concern applies. It is hard-coded to `xxh128`, and overriding `conditionalValidator()` is the escape hatch.
